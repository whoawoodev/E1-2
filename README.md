# 이산수학 기초 퀴즈 게임

터미널에서 동작하는 파이썬 콘솔 퀴즈 게임입니다.
문제를 풀고, 직접 문제를 등록하고, 최고 점수를 기록합니다.
프로그램을 껐다 켜도 추가한 퀴즈와 최고 점수가 그대로 남습니다.

## 퀴즈 주제와 선정 이유

주제는 **이산수학 기초**입니다.

컴퓨터공학 과정에서 배우고 있는 내용이라 정답뿐 아니라 왜 그 답이 되는지까지
스스로 설명할 수 있었습니다. 명제, 집합, 진리표처럼 답이 하나로 정해지는 개념이 많아
선택지 4개 중 하나를 고르는 형식과도 잘 맞았습니다.

오답 선택지를 아무 값으로나 채우지 않고, 역·이·대우를 헷갈리거나
부분집합 개수를 2^n 대신 n^2로 세는 것처럼 실제로 틀리기 쉬운 지점을 넣었습니다.

## 실행 방법

Python 3.10 이상이 필요하며, 외부 라이브러리는 쓰지 않습니다.

```bash
git clone https://github.com/whoawoodev/E1-2.git
cd E1-2
python3 main.py
```

## 기능 목록

| 메뉴 | 기능 | 설명 |
| --- | --- | --- |
| 1 | 퀴즈 풀기 | 풀 문제 수를 고르면 무작위 순서로 출제하고, 점수를 계산해 최고 점수와 기록을 남깁니다. |
| 2 | 퀴즈 추가 | 문제·선택지 4개·정답 번호·힌트를 입력받아 목록에 넣고 바로 저장합니다. |
| 3 | 퀴즈 목록 | 등록된 문제를 번호와 함께 보여줍니다. |
| 4 | 점수 확인 | 최고 점수와 최근 게임 기록 5개를 보여줍니다. |
| 5 | 퀴즈 삭제 | 번호를 골라 퀴즈를 지웁니다. 0을 누르면 취소합니다. |
| 6 | 종료 | 저장한 뒤 프로그램을 끝냅니다. |

### 선택 구현 기능

- **무작위 출제** — `random.sample()`로 매번 다른 순서로 출제합니다.
- **문제 수 선택** — 등록된 문제 수 안에서 몇 문제를 풀지 고를 수 있습니다.
- **힌트** — 정답 대신 `0`을 누르면 힌트가 나옵니다. 한 번당 5점이 깎이고,
  같은 문제에서 여러 번 눌러도 한 번만 계산합니다. 힌트가 없는 문제는 차감하지 않습니다.
- **퀴즈 삭제** — 목록에서 번호를 골라 지우고 파일에 반영합니다.
- **점수 기록** — 게임이 끝날 때마다 날짜·시각, 푼 문제 수, 점수를 남깁니다.

### 입력 처리 기준

- 입력값의 앞뒤 공백을 제거한 뒤 처리합니다. (` 1 ` → `1`)
- 숫자가 아닌 값, 허용 범위 밖의 숫자, 빈 입력은 안내 메시지를 출력하고 다시 묻습니다.
- `Ctrl+C`나 입력 스트림 종료로 중단되어도 데이터를 저장하고 정상적으로 끝냅니다.
- `state.json`이 없으면 기본 퀴즈로 시작하고, 파일이 손상된 경우 안내 후 기본 퀴즈로 복구합니다.

역할을 나눈 기준은 **바뀌는 이유가 다른 코드를 같은 파일에 두지 않는 것**입니다.
문제의 형태가 바뀌면 `quiz.py`, 저장 방식이 바뀌면 `storage.py`,
화면 흐름이 바뀌면 `quiz_game.py`만 고치면 됩니다.

파일 이름은 클래스가 들어 있으면 클래스명을 그대로 따랐고(`Quiz` → `quiz.py`,
`QuizGame` → `quiz_game.py`), 클래스가 없는 파일은 역할 이름을 썼습니다(`storage.py`, `main.py`).

## 데이터 파일 설명 (state.json)

- **경로**: 프로젝트 루트의 `state.json` (`storage.py`에서 실행 위치와 무관하게 절대경로로 지정)
- **인코딩**: UTF-8 (`ensure_ascii=False`로 한글을 그대로 저장)
- **생성 시점**: 첫 실행에서 퀴즈를 풀거나 추가하거나 종료할 때 만들어집니다.
- **없을 때**: `storage.make_default_quizzes()`의 기본 6문항으로 시작합니다.

### 스키마

| 필드 | 타입 | 설명 |
| --- | --- | --- |
| `quizzes` | list | 퀴즈 목록 |
| `quizzes[].question` | str | 문제 문장 |
| `quizzes[].choices` | list(str) | 선택지 4개 |
| `quizzes[].answer` | int | 정답 번호 (1\~4) |
| `quizzes[].hint` | str | 힌트 문장. 없으면 빈 문자열 |
| `best_score` | int | 최고 점수 (0\~100). 정답 수 ÷ 푼 문제 수 × 100에서 힌트 차감분을 뺀 값 |
| `history` | list | 게임 기록 목록 |
| `history[].played_at` | str | 플레이 시각 (`YYYY-MM-DD HH:MM`) |
| `history[].count` | int | 그 판에서 푼 문제 수 |
| `history[].score` | int | 그 판의 최종 점수 |

```json
{
  "quizzes": [
    {
      "question": "원소가 3개인 집합의 부분집합은 모두 몇 개인가?",
      "choices": ["3개", "6개", "8개", "9개"],
      "answer": 3,
      "hint": "원소마다 넣는다/안 넣는다 두 가지 선택이 있습니다."
    }
  ],
  "best_score": 83,
  "history": [
    { "played_at": "2026-08-21 09:14", "count": 6, "score": 83 }
  ]
}
```

점수를 정답 개수가 아니라 백분율로 저장한 이유는, 퀴즈를 추가할 수 있고 풀 문제 수도
고를 수 있기 때문입니다. 개수로 두면 6문제 중 5개와 10문제 중 5개가 같은 값이 되어
비교가 되지 않습니다.

`hint` 필드는 나중에 추가한 항목이라, 이 필드가 없는 예전 저장 파일도 읽을 수 있도록
`data.get("hint", "")`으로 기본값을 주었습니다. `history`도 같은 방식입니다.

## 코드 구조 및 설계

### Quiz와 QuizGame의 책임을 어떻게 나눴나

기준은 **"문제 한 개가 아는 것"과 "게임 전체가 아는 것"**입니다.

`Quiz`는 문제 하나에 대한 것만 압니다. 문제 문장·선택지·정답 번호·힌트를 들고 있고,
자기를 화면에 출력하거나(`show`) 주어진 번호가 자기 정답인지 알려주는(`is_correct`) 일만 합니다.
다른 문제가 몇 개인지, 지금 점수가 몇 점인지는 모릅니다.

`QuizGame`은 반대로 전체를 압니다. 퀴즈 목록·최고 점수·게임 기록을 들고 메뉴를 돌리고 점수를 계산합니다.
대신 개별 문제의 정답이 뭔지는 직접 보지 않고 `quiz.is_correct(picked)`에게 물어봅니다.

이렇게 나눠서 얻은 실질적인 이득이 있습니다.
**힌트 기능을 추가할 때 `quiz.py`만 건드렸고 정답 판정 코드는 손대지 않았습니다.**
한 클래스에 다 넣었으면 기능을 추가하다 정답 데이터에 실수로 닿을 수 있는데,
나눠두면 건드릴 수 있는 범위 자체가 좁아집니다.

입력 검증은 `ask_number`, `ask_text` 두 함수로 클래스 밖에 뒀습니다.
숫자를 받는 자리가 메뉴 선택·문제 수 선택·정답 입력·퀴즈 추가까지 네 군데인데,
검증 규칙을 각자 쓰면 한 군데만 빠뜨려도 규칙이 깨집니다.
게임 상태와 무관하게 "문구와 범위를 받아 숫자를 돌려주는" 일만 하므로 `self`가 필요 없습니다.

### state.json 읽기/쓰기가 어디에서 어떤 순서로 발생하나

**읽기는 시작할 때 한 번뿐이고, 쓰기는 데이터가 바뀔 때마다 일어납니다.**

읽기 순서 —

1. `main()`이 `QuizGame()`을 만듭니다
2. `__init__`이 `storage.load_state()`를 부릅니다
3. `state.json`이 없으면 기본 퀴즈 6문항으로 시작하고, 있으면 읽어서 `Quiz` 객체로 되살립니다
4. 결과를 `self.quizzes`, `self.best_score`, `self.history`, `self.loaded`에 나눠 담습니다

이후로는 메모리 안의 객체만 다루고 파일을 다시 읽지 않습니다.

쓰기는 데이터가 실제로 달라지는 세 지점에서만 `self.save()`를 부릅니다 —
퀴즈를 추가한 직후(`add_quiz`), 삭제한 직후(`delete_quiz`), 한 판이 끝나고 기록을 남긴 직후(`play`).
여기에 예외 경로가 하나 더 있어서, Ctrl+C로 중단되면 `main.py`에서 `game.save()`를 한 번 더 부릅니다.

`save()`는 자기가 직접 파일을 쓰지 않고 `storage.save_state()`에게 넘깁니다.
그쪽에서 `Quiz` 객체들을 `to_dict()`로 딕셔너리로 바꾼 뒤 `json.dump`로 씁니다.

### Ctrl+C나 EOF 상황에서 안전 종료를 위해 어떤 처리를 했나

`main.py`에서 게임 전체를 `try/except`로 감쌌습니다.

```python
def main():
    game = QuizGame()
    try:
        game.run()
    except (KeyboardInterrupt, EOFError):
        print("\n\n입력이 중단되었습니다. 데이터를 저장하고 종료합니다.\n")
        game.save()
```

`KeyboardInterrupt`는 Ctrl+C, `EOFError`는 입력 스트림이 끊긴 경우(Ctrl+D, 파이프 입력이 끝난 경우)입니다.
이 처리가 없으면 스택 트레이스가 쏟아지면서 비정상 종료됩니다.

위치를 `main.py`로 잡은 이유는, 중단 신호가 `input()`이 있는 어느 자리에서든 날아올 수 있기 때문입니다.
메뉴에서든 정답 입력 중이든 퀴즈 추가 중이든 바깥으로 튀어나오므로,
제일 바깥에서 한 번 받는 것이 모든 경우를 덮습니다. 안쪽마다 `try`를 두면 빠뜨리는 자리가 생깁니다.

퀴즈 추가 도중에 중단하면 입력하던 문제는 저장되지 않습니다.
`self.quizzes.append(...)`가 아직 실행되지 않았기 때문에 이미 확정된 데이터만 저장됩니다.

### 커밋을 어떤 단위로 나누었고 메시지 규칙은 어떻게 정했나

**기능 하나 = 커밋 하나**를 단위로 잡았습니다.
메뉴 → Quiz 클래스 → 기본 데이터 → 퀴즈 풀기 → 추가 → 목록 → 점수 → 저장/불러오기
→ 리팩터 → 예외 처리 → 선택 과제 3건 → README → clone/pull 순입니다.
이렇게 나누면 커밋 하나를 되돌렸을 때 기능 하나만 사라집니다.
여러 기능을 한 커밋에 묶으면 하나만 되돌릴 방법이 없습니다.

메시지는 **접두어 + 변경 요약**으로 통일했습니다.
`Feat:` 새 기능(12개) / `Fix:` 예외 처리 보강(1개) / `Docs:` 문서(2개) / `Refactor:` 동작은 그대로 두고 코드 정리(1개).

`Refactor`를 쓴 곳은 저장 형태로 바꾸는 코드를 `storage`에서 `Quiz.to_dict()`로 옮긴 커밋입니다.
기능은 하나도 안 변했고 어느 쪽이 그 일을 맡느냐만 바뀌었기 때문에 `Feat`가 아니라 `Refactor`로 적었습니다.

접두어를 붙이는 이유는 **로그만 훑어도 변경 종류가 갈리기 때문**입니다.
`update`나 `수정` 같은 메시지만 늘어서 있으면 커밋을 하나씩 열어봐야 합니다.

## 핵심 기술 원리

### 클래스를 쓴 이유는 무엇이며, 함수만으로 만들 때와 어떤 차이가 있나

**값과 그 값을 다루는 동작을 한 덩어리로 묶기 위해서**입니다.

클래스 없이 만들면 문제 하나가 딕셔너리가 됩니다.

```python
{"question": "...", "choices": [...], "answer": 2, "hint": "..."}
```

이러면 정답 판정을 할 때마다 바깥에서 `q["answer"] == picked`라고 써야 합니다.
이 코드가 여기저기 흩어지고, 나중에 정답을 번호가 아니라 문자열로 바꾸기라도 하면
흩어진 자리를 전부 찾아 고쳐야 합니다.

클래스로 묶으면 그 지식이 `Quiz` 안에만 있습니다.

```python
quiz.is_correct(picked)
```

바깥은 정답이 번호인지 문자열인지 알 필요가 없습니다. 판정 방식이 바뀌어도 `is_correct` 한 곳만 고치면 됩니다.

차이를 한 줄로 말하면 — **함수만 쓰면 데이터 구조를 아는 코드가 흩어지고, 클래스로 묶으면 그 지식이 한 곳에 갇힙니다.**
`QuizGame`도 마찬가지입니다. 퀴즈 목록·최고 점수·게임 기록 세 가지를 함수만으로 다루면
모든 함수에 세 개를 매번 넘겨야 하지만, 객체가 들고 있으면 `self`로 꺼내 씁니다.

### JSON으로 저장하는 이유와 JSON 형식의 특징은 무엇인가

프로그램이 켜져 있는 동안에만 존재하는 리스트·딕셔너리를 껐다 켜도 남기려면 파일에 써야 하는데,
파일에는 **글자만** 들어갑니다. 파이썬 객체를 그대로 밀어넣을 수 없습니다.
그래서 값을 글자로 적는 약속이 필요하고, JSON이 그 약속입니다.

JSON을 고른 이유는 세 가지입니다.

1. **파이썬의 자료구조와 모양이 거의 같습니다.** JSON의 객체는 딕셔너리로, 배열은 리스트로 그대로 옮겨집니다
2. **표준 라이브러리만으로 됩니다.** `import json` 한 줄이면 되고 "외부 라이브러리 없이" 제약과도 맞습니다
3. **사람이 열어서 읽을 수 있습니다.** 저장이 제대로 됐는지 파일을 그냥 열어보면 확인됩니다

형식의 특징으로는 담을 수 있는 종류가 정해져 있다는 점이 중요합니다.
문자열·숫자·참거짓·null·배열·객체뿐이라 파이썬 객체는 그대로 못 들어갑니다.
그래서 저장 직전에 `to_dict()`로 딕셔너리로 바꾸고, 불러올 때 다시 `Quiz()`로 되살리는 왕복 구조를 만들었습니다.

한글 때문에 `ensure_ascii=False`를 줬습니다. 기본값이면 한글이 유니코드 이스케이프로 박혀서 사람이 못 읽습니다.
`indent=2`는 줄바꿈과 들여쓰기를 넣어 읽기 좋게 하는 옵션입니다.

### 파일 입출력에서 try/except가 필요한 이유는 무엇인가

파일은 **프로그램 바깥에 있는 것**이라, 코드가 아무리 맞아도 실패할 수 있기 때문입니다.
변수는 내가 만든 것이지만 파일은 사용자도 열 수 있고 디스크 사정에도 걸립니다.

읽을 때 실제로 일어날 수 있는 실패를 종류별로 잡았습니다.

| 예외 | 언제 나는가 |
| --- | --- |
| `json.JSONDecodeError` | 파일이 JSON 모양이 아님. 누가 열어서 편집하다 망가뜨린 경우 |
| `KeyError` | `state["quizzes"]`를 찾는데 그 키가 없음. 형식이 다른 파일인 경우 |
| `ValueError` | `int(state["best_score"])`가 실패. 점수 자리에 숫자가 아닌 게 들어간 경우 |
| `TypeError` | 기대한 것과 자료형이 다른 경우 |
| `OSError` | 권한이 없거나 읽는 도중 문제가 생긴 경우 |

쓸 때는 `OSError`를 잡습니다. 디스크가 꽉 찼거나 권한이 없는 경우입니다.

읽기 쪽에서 잡는 종류가 더 많은 이유는 **바깥에서 들어오는 데이터를 믿을 수 없기 때문**입니다.
쓰기는 내가 만든 값을 내보내는 것이라 형식 문제가 날 일이 없고 환경 문제만 남습니다.

빈 목록도 손상으로 봅니다. 퀴즈가 하나도 없는 상태로는 게임이 성립하지 않아서,
`raise ValueError`로 일부러 예외를 내고 기본 퀴즈로 복구하게 했습니다.

### 브랜치를 나눈 이유와 병합의 의미는 무엇인가

브랜치는 **main을 건드리지 않고 따로 작업할 자리**를 만드는 것입니다.

퀴즈 풀기 기능을 `feature/play`에서 만들었습니다. 이 기능은 출제·정답 판정·결과 표시·빈 목록 처리까지
커밋 두 개짜리 작업이라, 중간 상태에서는 프로그램이 온전히 돌지 않는 구간이 있습니다.
그동안 main은 기본 퀴즈 데이터까지 완성된 상태 그대로 남아 있습니다.
실제 협업에서는 이 점이 더 중요합니다. 여러 사람이 각자 갈래에서 작업하면 서로의 미완성 코드에 부딪히지 않습니다.

병합은 **갈래에서 한 작업을 다시 main으로 합치는 것**입니다.
기능이 완성돼 프로그램이 온전히 도는 것을 확인한 뒤에 합쳤습니다.

`--no-ff`를 붙인 이유가 따로 있습니다. 갈래를 친 뒤 main이 하나도 안 변했으면
Git은 병합 커밋을 만들지 않고 main 표시만 앞으로 밀어버립니다(fast-forward).
그러면 로그가 일직선이 되어 **갈라졌다 합쳐진 흔적이 남지 않습니다.**
`--no-ff`는 병합 커밋을 강제로 만들어 그 흔적을 남깁니다.

```
*   Merge: 퀴즈 풀기 기능을 main에 병합
|\
| * Feat: 풀이 결과 표시와 빈 목록 처리 추가
| * Feat: 퀴즈 출제와 정답 판정 구현
|/
* Feat: 이산수학 기본 퀴즈 6문항 추가
```

이력을 봤을 때 "이 두 커밋은 하나의 기능을 만들던 묶음"이라는 게 그래프로 드러납니다.

### state.json 구조를 지금 형태로 설계한 이유는 무엇인가

**최상위를 배열이 아니라 객체로 한 이유** — 퀴즈 목록만 저장하면 배열로 충분하지만
최고 점수와 게임 기록도 같이 남겨야 합니다. 객체로 두면 나중에 항목이 늘어도 키를 하나 더 붙이면 됩니다.
실제로 힌트와 히스토리는 나중에 추가했는데 구조를 갈아엎지 않았습니다.

**정답을 문자열이 아니라 번호(1~4)로 둔 이유** — 사용자는 번호를 입력하므로 비교가 번호끼리로 끝납니다.
문자열로 두면 띄어쓰기나 오타까지 신경 써야 합니다.
화면 번호도 `enumerate(choices, start=1)`로 1부터 붙이므로 저장된 번호와 그대로 맞습니다.

**히스토리를 딕셔너리의 리스트로 둔 이유** — 한 판이 날짜·문제 수·점수 세 값의 묶음이라,
이름표가 붙은 딕셔너리가 자리 순서만 있는 배열보다 안전합니다. 나중에 항목이 늘어도 순서가 꼬이지 않습니다.

**힌트를 별도 파일이 아니라 퀴즈 안에 넣은 이유** — 힌트는 문제에 종속된 값이라 문제와 같이 움직여야 합니다.
퀴즈를 지우면 힌트도 같이 사라지는 게 맞습니다.

## 심층 인터뷰

### 퀴즈가 1000개 이상으로 늘어나면 지금 JSON 방식에 어떤 한계가 생기나

가장 큰 문제는 **부분 수정이 안 된다**는 점입니다.
지금 구조는 퀴즈 한 개를 추가하거나 삭제해도 `save_state`가 전체를 다시 씁니다.
1000개짜리 파일이면 한 문제를 지우려고 999개를 다시 기록하는 셈입니다.
읽기도 마찬가지로 `json.load`가 전체를 통째로 읽어 메모리에 올립니다.

이어서 세 가지가 더 걸립니다.

- **검색이 전부 순회입니다.** 주제별 필터 같은 기능을 붙이면 매번 1000개를 처음부터 훑어야 합니다. JSON에는 색인이 없습니다
- **쓰는 도중 중단되면 파일 전체가 깨집니다.** 원본을 `"w"`로 열어 바로 덮어쓰기 때문에, 그 사이에 프로그램이 죽으면 잘린 JSON이 남고 기존 데이터까지 통째로 잃습니다. 파일이 클수록 이 창이 넓어집니다
- **동시에 두 개를 켜면 나중에 저장한 쪽이 앞의 것을 덮어씁니다.** 파일 하나를 통째로 쓰는 방식에는 잠금이 없습니다

대안은 규모에 따라 다릅니다. 수천 개 수준까지는 **원자적 쓰기**로 손상 위험만 없애도 실용적입니다.
임시 파일에 먼저 쓰고 성공하면 `os.replace`로 갈아끼우는 방식입니다.
그보다 커지면 **SQLite**가 맞습니다. 표준 라이브러리(`sqlite3`)라 외부 의존이 늘지 않으면서
한 행만 수정하고 색인으로 검색하고 잠금까지 얻습니다.

다만 지금 규모(6~수십 문항)에서는 JSON이 맞다고 봅니다.
실행할 때 한 번 읽고 데이터가 바뀔 때만 쓰는 정도라 성능 문제가 없고,
사람이 파일을 열어 확인할 수 있는 이점이 더 큽니다.

### state.json이 손상돼 파싱에 실패하면, 데이터를 잃지 않도록 어떤 대응이 가능한가

지금 코드는 **읽기에 실패하면 안내를 띄우고 기본 퀴즈 6문항으로 복구합니다.**
명세가 요구한 "파일이 손상되었으면 안내 메시지를 출력하고 기본 퀴즈 데이터로 복구"가 이 동작이고,
저장 파일이 한 글자만 깨져도 프로그램이 실행조차 못 하는 상황을 여기서 막습니다.

여기서 한 걸음 더 나가 **원본 데이터 자체를 지키는 것**까지 목표로 삼으면, 세 개의 층을 얹을 수 있습니다.

1. **손상 파일을 옮겨두기** — 읽기에 실패한 시점에 `state.json`을 `state.json.corrupted`로 이름을 바꿉니다. 이후의 저장이 원본을 덮지 않으므로, 부분적으로만 깨진 파일은 나중에 열어서 살릴 수 있습니다. 코드 두세 줄이면 되고 지금 구조를 바꾸지 않습니다
2. **저장을 원자적으로 하기** — `state.json.tmp`에 먼저 쓴 다음 `os.replace()`로 갈아끼웁니다. 운영체제 수준에서 통째로 바뀌므로 중간 상태가 남지 않고, 쓰는 도중 프로그램이 죽어도 기존 파일은 그대로입니다. 손상 자체를 예방하는 층입니다
3. **직전 버전 백업 두기** — 저장에 성공할 때마다 이전 파일을 `state.json.bak`으로 남깁니다. 읽기에 실패하면 백업을 먼저 시도하고 그것도 실패할 때 기본값으로 갑니다

셋을 같이 쓰면 복구 순서가 **정상 파일 → 백업 → 기본값**의 3단이 됩니다.

이번 과제에서 기본값 복구까지로 범위를 잡은 것은, 명세가 요구한 지점이 거기였고
저장 시점이 한 판이 끝날 때 정도로 드물어 세 층의 비용이 얻는 것보다 크다고 봤기 때문입니다.
저장이 잦거나 데이터가 계속 쌓이는 프로그램이라면 2번은 기본으로 넣는 층입니다.

### 채점 방식이나 퀴즈 구조가 바뀐다면 어떤 파일을 먼저 수정해야 하나

**채점 방식이 바뀌는 경우 — `quiz_game.py` 한 곳입니다.**

점수 계산은 `play()` 안 세 줄에 모여 있습니다.

```python
base_score = round(correct / count * 100)
penalty = hint_count * HINT_PENALTY
score = max(base_score - penalty, 0)
```

부분 점수를 주든 문제별 배점을 다르게 하든 이 세 줄과 상수 `HINT_PENALTY`만 건드리면 됩니다.
`Quiz`는 정답 여부만 알려주고 점수는 모르기 때문에 `quiz.py`를 열 일이 없습니다.

다만 문제별 배점처럼 **점수가 문제에 붙는 형태**로 바뀌면 범위가 커집니다.
`Quiz`에 `points` 속성이 생기고 `to_dict()`와 복원 코드, `state.json` 스키마까지 따라 바뀝니다.
이 경우엔 `quiz.py` → `storage.py` → `quiz_game.py` 순이 맞습니다. 데이터 구조가 먼저 정해져야 나머지가 따라옵니다.

**선택지 개수가 바뀌는 경우 — 출력이 아니라 입력 쪽입니다.**

4지선다를 5지선다로 늘린다고 할 때, 화면에 뿌리는 코드는 손댈 것이 없습니다.
`Quiz.show()`가 `enumerate(self.choices, start=1)`로 돌기 때문에 선택지가 몇 개든 그대로 출력됩니다.
문제 객체도 리스트를 그대로 들고 있어서 개수를 따로 알지 않습니다.

바뀌는 곳은 값을 받아들이는 네 자리입니다.

- `quiz_game.py`의 `add_quiz` — 선택지를 몇 개 입력받을지
- 같은 함수의 정답 번호 입력 범위
- `play()`의 정답 입력 범위 (0은 힌트라 하한이 따로 있습니다)
- `storage.py`의 `DEFAULT_QUIZ_DATA` — 기본 문항이 들고 있는 선택지

네 자리가 같은 값을 공유하므로 `CHOICE_COUNT = 4` 같은 상수로 모아 두면
한 줄을 고쳐서 전부 따라오게 만들 수 있습니다.
힌트 차감 점수를 `HINT_PENALTY`로 둔 것과 같은 방식입니다.

정리하면 — **채점 규칙은 `quiz_game.py` 한 곳, 문제의 형태는 `quiz.py`부터 시작해
`storage.py`, `quiz_game.py` 순**입니다. 데이터 구조가 먼저 정해져야 나머지가 따라오기 때문입니다.
